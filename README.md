# Access Risk Analyzer

A practice project that scores simulated access requests for risk, recommends a review path, and enforces review rules: no self-approval, no repeat approvals by one person, two different approvers for high and critical risk, and locked decisions.

> **Authorship:** Written by AI (Claude), working in a Cloudflare OS session with a human reviewer directing the work. All people, requests, and data are simulated.

This is a learning project. It is not a real access-control system and should not be used to make real access decisions.

## What's in this repo

- **Root folder (this project):** the app as a standalone Node.js project. Runs on your computer. Follow the Quick start below.
- **`gadget/` folder:** the same app built as a Cloudflare OS Gadget (`server.js`, `client.js`). It runs only inside Cloudflare OS, not on your computer. It also includes `sample-data.json`, a read-only snapshot of the Gadget's simulated data. See `gadget/README.md`.

## Quick start

You need Node.js 18 or newer. Then run:

```bash
npm run setup
npm start
npm test
```

`npm run setup` creates the simulated users and prints their tokens once. `npm start` runs the app. `npm test` runs the tests.
## Requirements

- Node.js 18 or newer. No npm packages are needed.

## Run it

```bash
npm run setup     # creates data/users.json with 11 simulated people and prints their tokens once
npm start         # opens the app at http://127.0.0.1:3000
```

Open the page, paste a token from the setup output, and sign in. Each token belongs to one person. Use "Load simulated requests" on an empty queue to add six example requests.

To run on another port: `PORT=8080 npm start`.

To reset the data, stop the server and delete `data/state.json`.

If you lose the tokens, run `npm run setup -- --force`. This replaces the users file, so old tokens stop working.

## Test it

```bash
npm test
```

The tests cover the scoring rules, input checks and their boundaries, review rules, the service and audit log, and the HTTP API. They use fixed clocks and simulated data, so results are repeatable.

## How it works

| File | Purpose |
| --- | --- |
| `src/policy.js` | The rules: usual access by job title, role risk, score thresholds, limits |
| `src/analyze.js` | Scores a request (0–100), sets the level and approvals needed, and writes the explanation |
| `src/validate.js` | Checks a new request. The requester is always the signed-in user |
| `src/review.js` | Applies approve, deny, or escalate. Pure: it returns a new request and an audit entry |
| `src/service.js` | Stores requests and the audit log. Runs changes one at a time |
| `src/auth.js` | Token sign-in. The server stores only SHA-256 hashes of tokens |
| `src/server.js` | HTTP server and JSON API under `/api`, plus the static page |
| `src/file-store.js` | Saves state to `data/state.json` using a write-then-rename |
| `public/` | The browser page (plain HTML, CSS, and JavaScript; no build step) |

### Scoring

Each rule adds points, and the total is capped at 100:

- Roles beyond the job's usual set (up to 30)
- Privileged roles (25, and always at least "high")
- Sensitive data (up to 20)
- Contractor with sensitive access (20)
- Permanent access (15) or long access over 90 days (10)
- Justification under 20 characters (15)
- Account not used for over 90 days (15)
- Requester is also the approver (30)
- Can change code and deploy it (15)

Levels: 60+ critical, 35+ high, 15+ medium, below 15 low. High and critical need two different approvers.

### Identity

The signed-in person is identified only by their token. The request body can't set who is acting. Requesters can't review their own requests. Each reviewer can approve a request once.

## Limitations

- **Tokens are a practice stand-in.** Sign-in uses one token per person, not a company login such as SSO. Anyone with a token acts as that person.
- **No real integrations.** Nothing connects to a directory, HR system, or ticketing tool.
- **Explanations are rule-based text**, not generated by a language model. `src/analyze.js` says where to plug one in.
- **Rejected decisions are logged**, but the audit log keeps only the last 500 entries.
- **Single process, single file.** It is built for one machine. It is not meant for many servers or heavy traffic.
- **The page is basic.** It has been checked for layout and text safety, but not for accessibility with a screen reader.
